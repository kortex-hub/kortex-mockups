Kortex CLI

Create and manage agentic coding workspaces directly from your terminal. The Kortex CLI provides powerful commands for automation, CI/CD integration, and headless operation.

Quick Start

# 1. Start a workspace with Claude agent $ kortex --claude --name my-workspace # 2. Inspect workspace to see all resources and configuration $ kortex workspace inspect my-workspace # 3. Start working with a specific task $ kortex --claude --task "Refactor the authentication module"

Basic Commands

Start a new workspace

Create and start an agentic coding workspace with a specific agent

$ kortex --claude # Use Claude agent $ kortex --codex # Use Codex agent $ kortex --opencode # Use OpenCode agent

List workspaces

Display all existing workspaces and their status

$ kortex list $ kortex ls --running # Show only running

Stop a workspace

Stop a running workspace by name or ID

$ kortex stop frontend-refactor $ kortex stop --all # Stop all workspaces

Workspace Inspect

Inspect specific sections

Filter inspection output to specific resource types

# Show only sandbox information $ kortex workspace inspect api-refactor --section sandbox # Show only network configuration $ kortex workspace inspect api-refactor --section network # Show only available tokens $ kortex workspace inspect api-refactor --section tokens # Show only assets (filesystem, knowledge, skills, mcp) $ kortex workspace inspect api-refactor --section assets

Output formats

Export workspace configuration in different formats

# Output as JSON (useful for scripting) $ kortex workspace inspect api-refactor --json # Output as YAML $ kortex workspace inspect api-refactor --yaml # Quiet mode - show only values (for piping) $ kortex workspace inspect api-refactor --section sandbox -q
Flag Description Default
--section <name> Show only specific section: sandbox, assets, network, tokens all
--json Output in JSON format false
--yaml Output in YAML format false
-q, --quiet Minimal output, values only false
--show-secrets Show full token values (requires confirmation) false

Agent Options

Flag Description Default
--claude Use Claude Sonnet 4.6 as the coding agent -
--codex Use Codex for coding tasks -
--opencode Use OpenCode agent for coding tasks -

Flag Description Default
--task <description> Initial task description for the agent -
--name <name> Name for the workspace auto-generated
--dir <path> Working directory for the workspace .
--mcp <servers> Comma-separated list of MCP servers to enable filesystem
--skills <names> Comma-separated list of skills (local or enterprise from ocp.internal) -
--knowledge <id> Knowledge base ID to attach -
--devspaces Run workspace in Red Hat DevSpaces false

Network Policies

Configure network proxy policy

Set network filtering rules for a workspace sandbox

# Allow all traffic, block specific ranges (default) $ kortex workspace network proxy my-workspace \ --policy allow \ --block-cidr 10.0.0.0/8 \ --block-cidr 172.16.0.0/12 # Deny all traffic, allow only specific hosts $ kortex workspace network proxy my-workspace \ --policy deny \ --allow-host "*.anthropic.com" \ --allow-host "*.npmjs.org" \ --allow-host github.com

View network activity log

Monitor blocked and allowed network requests

$ kortex workspace network log $ kortex workspace network log --json # Machine-readable output $ kortex workspace network log --limit 50 # Show last 50 entries

Configure HTTPS bypass

Bypass HTTPS inspection for services with certificate pinning

$ kortex workspace network proxy my-workspace \ --bypass-host api.service-with-pinning.com # Bypass by CIDR range $ kortex workspace network proxy my-workspace \ --bypass-cidr 203.0.113.0/24
Flag Description Default
--policy <mode> Policy mode: allow (permit by default) or deny (block by default) allow
--block-cidr <cidr> Block traffic to IP range (can be repeated) RFC 1918
--allow-host <host> Allow traffic to host pattern (can be repeated) -
--block-host <host> Block traffic to host pattern (can be repeated) -
--bypass-host <host> Bypass HTTPS inspection for host (certificate pinning) -
--bypass-cidr <cidr> Bypass HTTPS inspection for IP range -

Advanced Examples

Full configuration example

Start a fully configured workspace with all options

$ kortex --claude \ --name "api-refactor" \ --task "Refactor the REST API to use async handlers" \ --dir ./backend \ --mcp filesystem,postgres,github \ --skills code-review,openshift-deployment,tekton-pipelines

Run in DevSpaces

Start workspace in Red Hat DevSpaces cloud environment

$ kortex --claude --devspaces \ --task "Set up CI/CD pipeline for the project"

Headless mode for CI/CD

Run workspace non-interactively with auto-approval

$ kortex --claude --headless --yes \ --task "Run all tests and fix any failures" \ --timeout 30m

Connect to OpenShift AI

Use models served from OpenShift AI platform

$ kortex --openshift-ai https://ai.openshift.example.com \ --model granite-3.1 \ --task "Analyze code for security vulnerabilities"

Quick commands

One-liners for common local agent setups

# List available models from RamaLama $ ramalama list # Initialize workspace with local coding agent using Qwen model $ kortex init --name my-project \ --agent opencode \ --model-provider ramalama:qwen # Start with a specific task $ kortex init --name my-project \ --agent opencode \ --model-provider ramalama:qwen \ --task "Add unit tests for the auth module"
Flag Description Default
--agent opencode Use OpenCode as the local coding agent -
--model-provider <provider:model> Specify model provider and model (e.g., ramalama:qwen, ramalama:granite) ramalama:granite-3.1
--local Force fully local execution (no external API calls) false
--gpu Enable GPU acceleration for local models auto
